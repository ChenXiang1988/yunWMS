# Design

## Context

- 存量分布：`wms-auth` 69 处判空 / 11 处 catch，`wms-master` 34 / 8，`wms-app` 6 / 0，`wms-web` 0。
- 判空不等于违规。现状里至少有三类必须保留：`api` 包入参断言、外部系统返回与报文解析、库存与金额写入前的不变式。
- `GlobalExceptionHandler` 已承担统一异常转换，`SaTokenAnnotationConfig`、`RestAuthResponses` 属跨边界兜底转换。
- 整改不产生新行为，但改错了会改变错误码与前端提示，前端无法从类型上发现。

## Goals / Non-Goals

**Goals:**

- 每条改动都能说出「谁在什么时候会触发这个判断」，答不出来的才删。
- 整改后对外可观测行为零变化：错误码、错误文案、HTTP 状态、日志关键字段保持原样。
- 每个模块一批提交，单批不超过 400 行。

**Non-Goals:**

- 不抽函数、不改分层结构、不做命名重构——那是另一件事，混进来会让 diff 无法判断行为是否不变。
- 不引入值对象改造（`docs/coding.md` 已定为建议项，非本 change 范围）。
- 不动测试断言。
- 不清理前端。

## Decisions

### D1. 用四类归档代替「全量删判空」

- 选择：整改前先产出 `audit.md`，每条给出「文件:行 + 归类 + 理由」，四类为重复判空、合法防御、无处理 catch、跨边界转换 catch。只改前两类中确属重复的部分，以及第三类。
- 理由：119 处判空里必然混着合法防御，机械删除会删掉外部报文解析和库存不变式；而这类错误在测试里未必暴露，等到线上才发现。
- 备选：脚本按模式批量删除 `if (x == null) throw`。否决，无法区分用户提示与契约断言。

### D2. 一条分支、按模块多次提交

- 选择：`change/clean-redundant-validation` 单分支，auth / master / app 各一批提交，每批 ≤400 行且结束时可编译可运行。auth 的 69 处判空预计需 2-3 批。
- 理由：`AGENTS.md` 定「一个 change = 一条分支」，「按模块拆多次提交」拆的是提交粒度，不是分支粒度。为拆分而派生多条分支，反而让同一套判据在不同分支上漂移。
- 触发拆分的条件：分支存活逼近 3 天仍未完成，或某模块切不出可编译的 400 行批次。届时按 `AGENTS.md`「须拆分」把未完成模块另开独立 change，并删除本条分支，不延期。
- 备选：三条并行的模块分支。否决，与「一个 change = 一条分支」直接冲突。

### D3. 行为不变是硬约束，遇到歧义就停

- 选择：整改中若某处判空实际承担错误码或文案语义（例如空值与业务异常共用同一提示），**不删、不改**，在 `audit.md` 标注「疑似语义承载，待确认」并上报。
- 理由：这类判断阅读时像冗余防御，实际是唯一产生该错误码的地方；删掉后行为改变，前端只表现为提示变了，测试若不覆盖文案就发现不了。

### D4. 先 auth，后 master，最后 app

- 选择：按存量规模与依赖方向排序。
- 理由：auth 存量最多且被 app 依赖，先做能暴露判据是否够用；app 存量少且有 bridge 装配，放最后可复用前两轮判据。

## Risks

- **删掉合法防御**：靠 D1 清单与「说出触发者」追问兜底；每批提交前用 `git diff` 逐条过一遍归类。
- **隐匿行为变更**：错误文案与错误码不在编译期受约束，只能靠测试与人工比对；tasks 中为每批安排一次文案比对。
- **批次膨胀**：单模块若超 400 行，`audit.md` 需要再切子批，不能为凑一批而放宽。
