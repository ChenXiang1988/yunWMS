# 文档规范

配合 `AGENTS.md` 的「文档」与「本文件的边界」两节。本文件讲细则，`AGENTS.md` 讲门禁。

## 一、四类文档

| 目录 | 性质 | 是否可改 | 读者预期 |
| --- | --- | --- | --- |
| `openspec/specs/` | 当前有效行为 | **必须始终最新**，改行为先改这里 | 描述系统现在怎么做 |
| `openspec/changes/` | 拟议变更 | 变更存续期内可改，归档后移出 | 描述即将怎么做 |
| `design.md` | 决策记录 | **只增不改**，新决策覆盖旧决策 | 描述当初为什么这么定 |
| `docs/research/` | 调研快照 | **不回改** | 描述调研当时看到了什么 |

第五类是 `git log`，它记录「谁在什么时候改了哪一行」，不占用文档位置。

### 判断方法

写文档前先问一句：**这份文件描述的是「现在」「将要」「当初为什么」还是「当时看到了什么」**。

答案决定它能不改，以及该不该标时效。

## 二、快照文档的时效标注

`docs/research/` 下的每份文档 **MUST** 在头部元信息中写明时效：

```markdown
# 某某主题调研

- 调研时间：2026-10-24
- 时效：本文为 2026-10-24 的快照，记录当时状态；后续变化以仓库现状为准，本文不回改。
- 适用对象：……
```

**为什么必须在头部**：

- 快照的问题不是「写错了」，是「写对了但过时了」。过时的事实比缺失的事实更危险，因为它会被当成现状使用。
- 头部一行覆盖全文，不随条目增多而增长；正文逐条加注则会越维护越乱。

### 内容过时时怎么处理

**MUST** 更新头部那句时效说明，**MUST NOT** 在正文里逐条加注「此后已修正」。

正文是证据。改写证据等于销毁证据；在证据旁边贴纸条，则会让证据本身变得不可读。

## 三、变更历史不打第二份

**MUST NOT** 建立 `CHANGELOG.md`。

理由：

- 项目不对外发布、无版本号，`CHANGELOG` 没有消费方
- `git log` 配合 Conventional Commits 已经是完整的变更记录，且不会漏记
- 两份历史一旦出现差异，没有任何机制能判断哪份是对的

需要「变更级」留痕时，记录在该 change 目录下的 `completion.md`，不写进规格、设计或调研正文。

## 四、change 交付记录

一个 change 进入验收前，在 `openspec/changes/<change>/completion.md` 记录：

```markdown
# 交付记录：<change-id>

## 目标与实际交付
（原计划做什么，实际做了什么，差异及原因）

## 关键设计
（实现中做出的、影响后续的决定，指向 design 的 D 编号）

## 验证结果
（Requirement → Task → Test → Result 的对应关系）

## 未验证项
（做不到或没做的验证，以及为什么）

## 已知风险
（上线后可能出问题的地方）
```

**为什么单独一份而不是写进 design**：design 是决策记录，回答「为什么」；completion 是交付记录，回答「做成了什么、验证了什么」。混在一起会让 design 无限膨胀，而 design 一旦膨胀就没人读。

## 五、文档改动本身

- 纯文档改动不需要开 change，但 **MUST** 检查路由、链接、引用与术语一致性
- 改动既有文档前先确认它的性质（见第一节），快照类不回改
- 术语以 `AGENTS.md` 的「术语」节为准，不在各处自行发挥
