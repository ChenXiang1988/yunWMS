## 1. 需求要点（R1）

### 1.1 问题陈述

起因是一个外部项目加一句传播说法：「单个 CLAUDE.md 封装四大原则，让 AI 减少约 80% 的无用代码」。要回答三个问题：

1. 这个 80% 是否成立？
2. 四条原则对本仓库现有交付协议有无实质增量？
3. 要不要把它的文件搬进来？

### 1.2 功能范围

| 域 | 内容 |
| --- | --- |
| 交付协议 | `AGENTS.md`、`.codebuddy/rules/*/RULE.mdc` 的行为约束条款 |
| 编码规范 | `docs/coding.md` 的变更范围、共享代码、测试三节 |
| 工具载体 | CodeBuddy 读取哪些指令文件，与 `CLAUDE.md` / `.cursor/rules` 的差异 |

不涉及任何业务模块，不涉及 WMS 领域口径。

### 1.3 关键特征

- **写码主体是 AI，人类只做验收**：任何「靠 AI 自述合规」的条款都无法验证，只能靠可机检的判据兜底。
- **规则已经很重**：`AGENTS.md` 100 行 + 3 份 alwaysApply 规则 + `openspec/config.yaml` rules 段 + `docs/coding.md` 50 行，再加文本的边际收益递减。
- **`AGENTS.md` 自带边界**：第 14–15 行限定「只放门禁、禁止项与路由」，新增约定超过 5 行必须落 `docs/<主题>.md`。这条直接决定了任何引入只能是一两行门禁。
- **载体不匹配**：本仓库用 CodeBuddy，不读 `CLAUDE.md`，也没有 `.cursor/`。
- **零授权预算**：只接受 MIT/Apache-2.0/BSD。

### 1.4 边界与非目标

**本期不做**

- 不评估 Claude Code 插件市场与 Cursor 生态的接入体验。
- 不做 A/B 评测：本仓库没有 Agent 行为评测集（见 `ai-coding-sustainability.md` 第 2 节），拿不到可信对照。
- 不改现有 `AGENTS.md`、`docs/coding.md` 的任何措辞——那要用户确认后另开 change。

**本期只判断**

80% 的真伪、内容增量、引入或不引入。

### 1.5 现存约束

- 交付纪律：单次提交 ≤ 400 行、一 change 一垂直切片、迁移与代码分离。
- 依赖准入三项：许可证、最近维护时间、能否被现有依赖替代。
- 规则的可执行性优先：`ai-coding-sustainability.md` 已把「文字纪律必须转成机器判定」定为方向，任何新增纯文本条款都要先回答「谁来判定」。

## 3. 「减少 80% 无用代码」核查

| 来源 | 数字 | 性质 |
| --- | --- | --- |
| 仓库 `README.md` / `README.zh.md` / `EXAMPLES.md` | **无任何百分比**；`1000 行 vs 100 行`、`200 行压到 50 行` 是修辞类比，不是统计值 | 已核 |
| CSDN 一篇「深度实践方案」 | 行数减少 50–70%、返工率降低 60%+、误解性实现减少 80%、效率提升 40% | 二手，四个数字互相不成体系，无出处 |
| bittide 转载短文 | 「up to 90%」 | 二手 |
| besthub 一篇对照文 | 同一任务 38 行 vs 95 行 | 二手，**n=1**，单任务单次，无重复实验 |
| 其他中文博客 | 常以「实测」为标题，正文复述 README 后加自造收益 | 二手，不作独立证据 |

结论：**「80%」没有一手依据**。它既不在仓库里，也不在任何可复现的评测中；同一条说法在传播链上有 50–70%、60%、80%、90% 四个版本，属典型营销放大。唯一可查的数字是一个单例对照（38 vs 95 行），样本量为 1，不足以支撑任何百分比。

顺带一个反证：star 从 2026-04 的 4 万量级涨到 10 月的 22.3 万（4 月读数来自二手博客），而同期仓库只有 28 次提交、最后合并停在 2026-04-20。**热度增长与内容演进脱钩**，star 反映传播，不反映效果。

## 5. 与本仓库现有条款逐条对照

| Karpathy 原则 | 本仓库现有覆盖 | 缺口 |
| --- | --- | --- |
| 1. 编码前思考：显式假设、多解释并列、提出更简方案、困惑即停 | `AGENTS.md` 37–40（先读文件、先列清单、需求不清停下来问、不猜业务口径）；`openspec/config.yaml` proposal rules | 「显式陈述假设」弱于「停下来问」；「更简方案要主动说」无对应条款 |
| 2. 简洁优先：不加功能/不为单次使用抽象/不加未要求的可配置性/不为不可能场景写错误处理/200 行压到 50 行 | `docs/coding.md` 7–9（变更 MUST 最小完整可验证；MUST NOT 预建抽象、接口、事件、扩展点；NEVER 空实现与伪成功） | 覆盖更严，**无缺口**；「200→50」是量化判据，但本仓库已有更可执行的「最小完整」 |
| 3. 精准修改：不动相邻代码、不重构没坏的、沿用既有风格、死代码只提示不删、只清自己造成的孤儿、每行改动可追溯 | `AGENTS.md` 44、47（禁止顺手重构/格式化、禁止未读整体改写）；`docs/coding.md` 10 | **三个缺口**：既有死代码只提示不删；孤儿代码只清自己造成的；「每行改动可追溯到请求」这一可判定标准 |
| 4. 目标驱动：定义成功标准、测试先行、计划带 verify、强标准可独立循环 | `AGENTS.md` 60–62（编译/单测/静态检查全过、交付说三件事、无法验证如实说明）；`openspec/config.yaml` tasks rules（每条任务可独立验证并写明验证方式） | 基本覆盖；「任务改写成可验证目标」已由 tasks rules 承担 |

**净增量：3 条，均为第 3 原则的细粒度边界。** 第 2 原则本仓库写得更严，第 1、4 原则只有措辞层面的微差。这就是「引入」能换来的全部。

## 6. 结论（R4）

**自行实现**——不引入该仓库的任何文件，只按本仓库措辞补齐第 5 节标出的 3 条缺口（是否补，见 Q1）。

不选「直接复用」的理由：

1. **载体不成立**：本仓库用 CodeBuddy，读 `AGENTS.md` 与 `.codebuddy/rules/*/RULE.mdc`，不读 `CLAUDE.md`；仓库也没有 `.cursor/`。`CURSOR.md` 自己写明「Cursor 默认不读 `CLAUDE.md`」——同样的道理适用于本仓库。搬文件等于放进一个没人读的目录。
2. **增量只有 2–3 句**：第 5 节逐条对照的结果。为 3 句话引入一个外部上游，维护成本大于收益。
3. **上游已冻结**：最后推送 2026-04-20，137 条 open 里抽查前 10 全部是未合并 PR（韩/日/印地语翻译、Codex/Copilot/OpenClaw 适配）。内容不会再演进，且三副本同步问题社区已提出但无人裁决。
4. **许可证有瑕疵**：根目录无 `LICENSE`，GitHub API `license` 为 `null`，仅 README 一行「MIT」。严格意义上不构成可分发授权；虽然本仓库只是借用措辞（思想不受版权保护），但没有必要在这个点上留记录。
5. **`AGENTS.md` 自限**：新增约定超过 5 行必须落 `docs/`。真要引入，落地形态也只能是一行门禁 + 两行细则，与「引入一个项目」无关。

不选 `obra/superpowers` 的理由：它是完整方法论框架（14 skills + 强制 TDD + worktree 流程），与本仓库已有的 OpenSpec 流程、`ai-coding-sustainability.md` 规划的门禁方向重叠，引入会换掉工作单元的定义。

**若用户要落地的最小动作（不改流程，仅 3 行）**

- `AGENTS.md`「禁止项」加 1 行：`禁止删除或"顺手清理"与本次任务无关的既有死代码，发现时只报告`。
- `docs/coding.md`「变更范围」加 1 行：`因本次改动而失效的导入/变量/函数 MUST 一并删除；预先存在的未使用代码 MUST NOT 删除`。
- `docs/coding.md`「变更范围」加 1 行判据：`每一行改动 MUST 能直接追溯到本次任务请求；追溯不到的行 MUST 撤回`。

第 3 条是本篇唯一认为值得抄的句子：它把「禁止顺手重构」从态度变成可判定标准。

## 7. 风险与待确认（R5）

### 7.1 风险

| 风险 | 说明 |
| --- | --- |
| 无法机检 | 四条原则全是行为约束，没有一条能进 CI。按 `ai-coding-sustainability.md` 的方向，纯文本条款的收益取决于模型是否真的执行，不可测 |
| 过度提问拖慢交付 | 作者自己在 `CLAUDE.md` 顶部承认「偏向谨慎而非速度」，琐碎任务需自行判断。本仓库交付节奏是「小切片、3 天内归档」，把「困惑即停」写死会与这个节奏冲突 |
| 与更严条款冲突时解释权不清 | `docs/coding.md` 的「最小完整可验证」比「简洁优先」更严；两条并存时 AI 会挑对自己有利的一条 |
| 上游漂移 | 若直接复制文本，日后无法回吸上游改动（上游已冻结，此风险实际很低） |
| 传播污染 | 二手文章把项目误归给 Karpathy、把收益抬到 80–90%。若在提案里引用这些数字，等于把营销材料写进决策依据 |

### 7.2 待确认

- **Q1**：是否补第 6 节那 3 行？补则另开 `chore/` 或 `docs/` 类 change，不与其他改动混提交。
- **Q2**：是否需要在 `AGENTS.md` 里显式写「参考了 Karpathy 的四条观察」作为出处？倾向不写——本仓库规则的有效性不依赖外部权威，写进去反而给后来者一个「按原文对齐」的错觉。
- **Q3**：是否要把「80%」这个说法在团队内纠正？如果要对外引用该项目的效果，只能引用「无一手数据」，不能引用任何百分比。

Q1 未闭环前，不修改任何现有规则文件。
