## 一、三轮收窄的过程（方法说明）

本次评审分三轮收窄，每轮换一个切面：

1. **结构与流程面**（分支、提交、任务进度、测试密度）
2. **安全 / 运维 / 生命周期面**（凭据、限流、依赖面、部署形态、tag、retention）
3. **治理体系自洽面**（规则与执行的一致性、机检覆盖、审计视野边界）

三轮的结论递进而非并列：表层（流程违约）由中层（架构欠账）解释，中层欠账之所以能长期存在，由深层（治理视野）解释。

## 三、优先级分歧与裁决记录

评审过程中出现两种排序函数，值得留档：

- **排序 A（按风险窗口紧迫性）**：S1（不可撤回的凭据泄露）排最前，理由是「已经发生且撤不回」。
- **排序 B（按对未来的杠杆）**：先拍板 MVP 方向与队列，理由是它决定接下来几周 AI 队列生产什么，而 S1 的利用窗口被「首次部署」这道还远未打开的门锁着。

**裁决采 B**，理由有三，均为仓库自身事实而非偏好：

1. **生命周期阶段**：无用户、无部署、无产品。S1–S5、S7 的风险窗口全部被「首次部署」锁住，而首次部署又被「产品存在」锁住——入库/库存/出库为零，部署在数月之外。这些项「现在修」与「部署前修」等价，MVP 方向「现在定」与「三周后定」不等价。
2. **协作结构**：本仓库的体系里人类只做验收与拍板，P4 类决策是唯一无法下派给子 Agent 的活——人类是瓶颈，瓶颈上的事天然最优先。
3. **主导失败模式**：治理文本已达主代码 79%，而核心域为零。当前最大的风险不是「带着漏洞上线」（门还没开），而是「过程精美、产品空心」（正在发生）。

**但排序 B 保留两条不随排序改变的底线**：

- S1 的泄露不可撤回，其修复**必须**绑定到部署门（写进部署前置清单或规格 Requirement），不能靠日后记性——「赶上线时安全清单第一个被扔」是知名失败模式。
- P4 是一个只消耗半天人类注意力的拍板动作，与 P0–P3 抢的不是同一份资源；真正的互斥对象是任何同样需要人类拍板的活。

## 四、改动的分块建议

> 排序原则：先拍板（人类）、再关门（在途 change）、再把「愿望」变成「闸门」、再还欠账、最后战略执行。
> 落地方式遵循本仓既有体系：能进 chore/ 分支的基建与文档由主 Agent 自做；业务代码、迁移、测试一律派发。本文档为快照，不指令任何在途 change。

### 第一块（拍板，半天人类注意力）

拍板 MVP 链条（货主建档 → 商品建档 → 入库 → 库存 → 出库）、验收形态（UI 级或集成测试级——直接决定 4.2–4.4 是否在关键路径）、队列顺序（建议：关 implement-owner → clean-redundant-validation → implement-sku → 入库；clean-redundant-validation 排 SKU 前的理由是判空传染成本随代码量上涨，此条可辩）、冻结 TTS / CAD / 视频监控类 speculative research 为 backlog、把 S1 修复钉进部署前置门。

### 第二块（关门，把最大伤口收掉）

implement-owner 拆分归档：4.2 / 4.3 / 4.4 前端三件套整体拆出为独立 change；后端小件（2.7b、2.9、3.4–3.6）凑一批收尾；归档删分支，恢复「一个 change 一个垂直切片」。

### 第三块（闸门，治理自洽）

- 修正 400 行口径（agents.md 第五节）：`src/test/**` 排除出上限或测试类单独放宽；docs 大宗提交（G6）纳入同一口径决策；改完即封账，存量债停止累积。
- `check-commit-size.sh` 接进 CI（push / PR 范围内逐笔检查）。
- 写平 G1：成文「合入 main 前允许重排且必须逐笔实测中间态可编译；合入后一律只登记」——这是已发生实践的事实成文，不是新规则。
- 内部验收走 PR：branch protection + 检查项 = CI + 行数机检 + audit.md 存在；README 措辞改为「外部 PR 不看，内部验收走 PR」。
- delivery-auditor 检查单加「安全与产品性」节：本次提交是否引入新凭据、是否扩大攻击面、是否新增无保留策略的追加表、是否新增无 CVE 扫描覆盖的依赖。

### 第四块（欠账，按痛感排）

移除 wms-auth 中零使用的 `spring-boot-starter-data-redis`（README 同步）；Dockerfile + prod compose 草案 + 备份 runbook（涉及 GPL 禁令需先按第 11 条思路澄清适用范围——运行时工具链与基础镜像不计）；每次归档打 tag；审计保留策略（规格补一条 + 定时清理）；前后端 lint 最小集；API 台账改由集成测试落盘 openapi.json 后在 CI diff（消除「需起后端才能再生成」的摩擦）；i18n 做了断（随 4.2/4.3 落地抽词条，或 design.md 记「en-US 期后目标」）；Excel 业务清单转 spec 附录或入 research 加快照头。

### 不建议做的（同样留档）

Valkey 会话层（单实例私有部署收益不成立，本仓调研已裁决「首期不做」）；任何新增治理文本（111 个 md 已超重，所有治理建议均为「改口径、进 CI」而非加文档）；外部协作机制（issue 模板、CONTRIBUTING——单出向仓库无消费方）；重写已合入的历史（G1 成文后此路关死）。

### 安全项的归位方式

S1–S4、S7 全部移入「首次部署前必须完成」的部署门清单（Definition of Deployable），不按日历排期；其中 S1 的门禁条件必须有约束力（规格 Requirement 或部署 checklist 硬条目），不可为纯提醒。IP 级限流（S2）与受信代理裁决（S4）可与登录相关的下一个业务 change 合并落地。

## 五、一句话收束

这个仓库的治理体系**善于发现问题，弱于强制止损**：三层缺陷几乎都能在它自己的 audit.md 与 research 里找到原话，自我认知在线；但「登记为存量」反复替代了「解决」——超限债在累积、implement-owner 超期硬撑、Valkey 装而不用、lint 空缺、安全面裸奔。下一步真正的考验不是再加一条规则，而是把 MVP 拍下来、让第一个业务域跑起来，否则「治理精度」与「业务空心」的剪刀差还会继续扩大。
