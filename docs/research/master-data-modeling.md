# yunWMS 主数据建模调研：多货主、仓库空间与商品标识

- 调研时间：2026-10-22
- 数据来源：Odoo 官方文档与源码（`stock.location`、`stock.quant`）、ERPNext 文档、GreaterWMS 与 ModernWMS 仓库、Amazon FBA 卖家文档、3PL 行业公开资料
- 结论状态：已采纳，对应 `design.md` D3 至 D9

## 1. 需求要点

| 维度 | 要求 |
| --- | --- |
| 货主 | 多货主共用仓库，库存按货主分账 |
| 仓型 | 平面仓、楼层仓、多栋楼仓共用一套模型 |
| 商品 | 全系统 30 万 SKUID，单仓有库存约 2 万 |
| 条码 | 同一款商品的条码可能在不同货主下重复出现 |
| 实物标识 | 仓库靠标签而不是商品条码识别归属 |

## 2. 候选系统与建模取向

| 系统 | 技术栈 | 空间建模 | 多货主 | 参考价值 |
| --- | --- | --- | --- | --- |
| Odoo Inventory | Python | 树形 `stock.location`，含 usage 类型与物化路径 | 通过公司或多库位模拟，非原生多货主 | 库位树与库存记账粒度 |
| ERPNext | Python / Frappe | 以仓库为库存粒度，货位层级较浅 | 多公司 | 简单场景的取舍 |
| GreaterWMS | Django + Quasar | 库区 / 货架 / 货位三层 | 单货主为主 | 作业界面与 PDA 流程 |
| ModernWMS | .NET + Vue3 | 轻量货位 | 单货主 | 前端交互参考 |
| 商业 AS/RS（如海柔 ESS） | — | 货架格位 + 精确坐标 | 设备侧 | 库位地图的形态 |

## 3. 空间建模的三种形态

### A. 仓库 + 货位两层

库存挂在「仓库 + 货位」上，没有更细的层级。适合 SKU 少、地堆为主的仓。

**问题**：楼层仓与多栋楼仓无法表达，跨层搬运、按楼层盘点都做不了。

### B. 树形库位 + 用途类型

Odoo 的做法：`stock.location` 是树，每条记录有 `usage` 字段区分用途：

| usage | 含义 |
| --- | --- |
| `internal` | 内部存储位 |
| `view` | 仅用于分组的虚拟节点 |
| `supplier` | 供应商位（收货的对方） |
| `customer` | 客户位（发货的对方） |
| `inventory` | 盘点调整用的虚拟位 |
| `transit` | 调拨在途 |
| `production` | 生产投料位 |

树用 `parent_path` 存物化路径，子树查询一条 `like` 就够。

**对我们的启发**：虚拟库位不需要单独一张表，用 `usage` 或 `location_kind` 标记即可；但虚拟库位不能进实体树，这一点比 Odoo 更严格。

### C. 树形 + 坐标 + 格位

自动化仓的做法：每个格位有行、列、层坐标，设备靠坐标取放。人工作业仓不需要，但库位地图需要。

**结论**：走 B 的结构，预留 C 的坐标字段，不实现 C 的调度。

## 4. 多货主隔离的三种粒度

| 粒度 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **行级** | 所有业务表带 `owner_id`，查询时过滤 | 库位利用率最高，同一库位可放多货主 | 每条查询都要带条件，漏一处即串数据 |
| 库位级 | 一库位只归一个货主 | 隔离天然成立，作业不易错 | 库位碎片化，小货主占用浪费 |
| 仓库级 | 一仓只服务一个货主 | 最简单 | 3PL 的核心价值就是共用仓，不可行 |

行业里 3PL 普遍用行级隔离，再叠加**库区级的货主归属**来降低作业风险：大货主划专属库区，小货主放共享区。

**我们的选择**：行级 `owner_id` 为主，库区可设专属货主作为作业约束。默认禁止同条码不同货主混放同一库位。

## 5. 商品标识的三个层次

| 层次 | 例子 | 谁分配 | 唯一范围 |
| --- | --- | --- | --- |
| 商品条码 | UPC `6973497202704` | 厂商 | 不唯一，多个货主可共用 |
| 货主商品编码 | `A-ERP-8821` | 货主 | 货主内唯一 |
| **仓库内部码** | `AMZ1000123` | 3PL 系统 | 全局唯一，货主级语义 |

### 行业实证：Amazon FBA 的 FNSKU

Amazon FBA 的场景与 3PL 高度相似：同一款商品由多个卖家销售，UPC 相同。FBA 的处理方式是给**每个卖家的每个商品分配独立的 FNSKU**，入仓前必须贴 FNSKU 标签，仓库按 FNSKU 识别归属，而不是扫 UPC。

这直接印证了我们的设计：**条码不能作为唯一标识，必须有一个系统分配、实物可贴的内部码**。

### 为什么内部码按货主分配而不是全局归一

理论上可以把同款商品归一成一个全局 SKU，货主各自映射。但这要求 3PL 预先维护全量商品库，并承担「这两条记录是不是同一款」的判断成本，而实际业务中不同货主之间并不需要共享任何商品属性。

代价是同款商品在两个货主下重复维护尺寸重量；换来的好处是编码生成零判断、货主之间零耦合。

## 6. 包装层级与托盘

调研中出现的两种做法：

| 做法 | 形态 | 问题 |
| --- | --- | --- |
| 固定四层字段 | 单品 / 内箱 / 外箱 / 托盘各存一组字段 | 大量空列，加第五层要改表 |
| 链式层级 | 一行一层，记录相对上一层的换算 | 灵活，层数由数据决定 |

**托盘的特殊性**：一个托盘通常混放多个 SKU，托盘规格由 3PL 决定而非商品属性。所以托盘不属于商品的包装层级，而是独立的**装载单元**，属于作业域。

**我们的选择**：链式表，最多到外箱；托盘在执行端作为装载单元建模。

## 7. 对 yunWMS 的结论

| 决策 | 依据 |
| --- | --- |
| D3 一棵树 + 运输资源 | Odoo 的树形库位验证了可行性；三种仓型靠层级开关而非三套表 |
| D4 虚拟库位同表 + 类型标记 | Odoo 用 `usage` 区分用途，我们加 `location_kind` 并强制不进实体树 |
| D5 SKUID 货主级唯一 | FBA 的 FNSKU 是直接先例 |
| D6 条码货主内唯一 | 同条码跨货主重复是常态，全局唯一会卡死建档 |
| D7 包装链式到箱 | 固定四层会留空列，且托盘不属于商品 |
| D8 组套归增值服务 | 套装是加工服务，不是商品属性 |
| D9 编码系统生成 + 别名 + 外部码 | 纯流水不可读，纯人工会重号 |

## 8. 被否方案

| 方案 | 否决原因 |
| --- | --- |
| 一仓一货主（仓库级隔离） | 3PL 的价值就是共用仓，与商业模式冲突 |
| 库位级独占货主 | 库位碎片化严重，小货主场景浪费过大 |
| 全局商品归一 + 货主映射 | 需要预先维护全量商品库，且承担归一判断成本 |
| 固定四层包装字段 | 空列多，扩展要改表 |
| 托盘进包装层级 | 托盘混放多 SKU，无法挂在单个商品上 |
| 库位坐标由 WMS 自建 | 若接入自动化设备，坐标以 WCS 为准，WMS 应存同步副本 |

## 9. 未验证项

- ERPNext 是否已提供货位级的库存粒度，本文按其公开文档的仓库粒度描述，未逐版本核对。
- 楼层仓与多栋楼仓的库位编码规则，行业中缺少公开的统一约定，本文的五段编码是为本项目设计，非行业标准。
- 各 AS/RS 厂商的库位码格式（如 `HAI-014-072-04_1@6`）无公开规范，映射方案需在与厂商对接时确认。
