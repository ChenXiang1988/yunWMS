# yunWMS 平台订单来源与接单模型调研

- 调研时间：2026-10-23
- 时效：本文为 2026-10-23 的快照，记录当时状态；后续变化以仓库现状为准，本文不回改。
- 来源资料：`docs/15个平台业务模式与单据类型全量清单_V1.1_含平台汇总.xlsx`（V1.1，核对日期 2026-10-21）
- 结论状态：草案。接单模型的设计原则已定；三项业务口径待确认（见第 6 节）。尚未绑定 OpenSpec change，未进入实现。

## 1. 需求要点

| 维度 | 结论 |
| --- | --- |
| 定位 | 多货主 3PL 云仓。仓内货主即三方平台卖家，仓内作业由平台订单驱动 |
| 订单来源 | 货主的平台订单，覆盖 15 个平台、94 个业务模式组合、114 个候选单据条目 |
| 我方承担的环节 | 只承接货物物理流经我方仓的部分：平台订单出库、发往平台仓的调拨出库、货主送仓与平台退货回仓的入库 |
| 明确非目标 | 不设计平台仓（FBA / FBT / FBO / FBW / FBA 类）内部作业规则；不设计全托管业务规则（由独立团队确认）；本期不直接对接平台接口 |

## 2. 来源资料盘点

### 2.1 表结构

| Sheet | 行数 | 作用 |

| `04_待核事项` | 56 | 待核清单，P0 27 条 / P1 29 条 |

### 2.2 证据分级

主表 `业务证据状态`：官方证据确认 58 条、行业证据官方待核 12 条、候选待核 44 条。`供应链阶段` 分布：销售 67、逆向 18、入仓 15、备货 5、发货 4、采购 3、采购备货 1、生产 1。

资料本身对边界的表述是准确的，值得沿用的有三条：

- 「官方证据确认」只表示业务模式或业务对象有公开官方证据，**不等于 API 可用或当前已授权**。
- 单据编码与模式编码是 ERP 拟定标识，不是平台官方枚举。
- 平台原始销售订单与仓库出库单、物流单有上下游关系，不能把所有下游内部单据当成平台原始 API 单据。

### 2.3 交叉核对结果

已核对通过，可作为后续校验项固化到脚本：

- `01` 表「关联单据数」合计 114，等于 `02` 表行数；逐模式编码比对，0 处不一致。
- `02` 与 `03` 的单据编码集合完全一致，无重复、无孤儿行。
- `02` 表单据编码唯一。

### 2.4 使用前必须处理的问题

| # | 问题 | 事实 |
| --- | --- | --- |
| 1 | API 层零验证 | `应用授权状态` 114/114 为「未验证」；`具体API/字段定位` 114/114 为「待填」；92 条写的是「平台级接口目录已收录，模式级端点待核」 |
| 2 | 待核清单覆盖不足 | `04` 仅 56 行，覆盖 56/114 个单据类型；56 行只用了两种措辞（44 条「需官方证明业务模式独立性」、12 条「业务已知，需按站点确认」），P0/P1 与证据状态不严格对应 |
| 3 | 售后单粒度不足 | 15 条售后单按平台各一行占位，未区分退款 / 退货退款 / 仅退款，未区分退平台仓与退我方仓 |
| 4 | 状态列与说明列矛盾 | 24 处：如 `M-009`～`M-012`（TikTok 跨境自运营、半托管、全托管）状态为「候选待核」，说明写「官方（美国站）」；`M-041`～`M-046`（Amazon SFP / Easy Ship / Vendor / DF）状态为候选，说明引用「官方 FBA 入仓 API 说明」，该文档与上述模式无关 |
| 5 | 缺关键字段 | 无站点 / 国家、无店铺与授权主体、无生效期与版本；但多条核实说明写「按站点确认」「区域性服务」 |
| 6 | 编码不可持续 | `M-001`～`M-094` 为全局流水号，无平台语义，增删一条即错位。建议改为 `平台:模式` 稳定键 |
| 7 | 源表未纳入版本控制 | 该 xlsx 目前在 git 中未跟踪，团队无法共享与 diff |

结论：**本表能证明业务对象存在，不能支撑接入排期。** 在问题 1、2、3 收敛前，不得据本表建立生产枚举。

## 3. 关键判断

### 3.1 视角错配

来源资料是**商家 ERP 视角**（列名为「ERP 调用权限」「ERP 拟定分类」）：商家收到平台订单，判断谁发货，然后自建仓、交给平台仓、或交给第三方仓。

yunWMS 是**多货主 3PL 云仓视角**。两者分歧点：

- 表内被判为「平台侧履约」的 `3PF`、`合作仓`、`海外仓`，在 3PL 视角下可能就是**我方仓**，恰恰是出库单来源。同一行条目在两套视角下归属相反。
- 表内完全没有 WMS 需要的作业维度：面单来源、时效承诺、贴标 / 换标 / 塑封、拆包与多包裹。Wildberries 的 DBS / DBS PVZ / EDBS / DBW / C&C 五种模式，仓内差异正好落在这些维度上，但表内只体现为 5 个不同的单据类型名。

### 3.2 「供应链阶段」不能直接换算成 WMS 单据方向

判断一条平台条目是否消耗我方仓产能，标准不是「谁发货」，而是**货有没有物理流经我方仓**。

| 表内条目 | 表内阶段 | 我方仓侧实际 | 原因 |
| --- | --- | --- | --- |
| `AMZ-004` FBA 入仓货件 | 入仓 | 出库（调拨出库，发往平台仓） | 货从我方仓发出 |
| `SHP-004` FBS 入仓 | 入仓 | 出库（同上） | 同上 |
| `WB-001` FBW 供货 | 入仓 | 出库（同上） | 同上 |
| `TTS-004` FBT 入仓 | 入仓 | 出库或零工作量 | 取决于是否经我方仓 |
| `LAZ-006` FBL 退仓 | 逆向 | 入库（平台仓退回我方仓） | 货回流 |
| `EMG-004` FBE 退仓 | 逆向 | 入库（同上） | 同上 |
| 15 条售后单 | 逆向 | 三态：退平台仓零工作量；退我方仓生成退货入库单；仅退款无实物 | 按退货落点判定 |
| 工厂直发平台仓 | 入仓 | 零工作量 | 货不经我方仓 |

`05_通用派生关系` 表的「平台供货单 / 备货单 → ERP 采购单」是 ERP 侧的派生物；到 WMS 层应落到「供货出库单」，方向相反。

### 3.3 履约归属三态

WMS 侧只需要三态，不需要 114 个单据类型：

| 归属 | 含义 | WMS 工作量 |
| --- | --- | --- |
| 平台仓履约 | 货在平台仓，我方只做头程 | 出库（调拨发往平台仓）或零 |
| 我方仓履约 | 含 3PF 代运营仓、合作仓 | 全链路出库（拣货 → 复核 → 发货） |
| 不流经我方仓 | 工厂直发平台仓等 | 零，仅 ERP 侧分流标签 |

同一货主、同一批货可能同时存在三种状态，属常态。

## 4. 方案取向

### 4.1 设计原则：留口不留路

订单入口存在两条候选路径，均未最终确定：

- **A. 货主 ERP 推单**（当前倾向）
- **B. 货主端直连平台**（凭证需按货主隔离存储、可吊销、可审计，是独立模块）

两条路最终收敛到同一接单契约。本期**只固定契约，不建任何平台适配器**。

### 4.2 接单契约三要素

| 要素 | 内容 | 理由 |
| --- | --- | --- |
| 来源与幂等 | `source_type`（ERP 推单 / 货主端录入 / 平台直连）+ 外部单号 + 货主 + 店铺 + 站点；幂等键 = 来源 + 外部单号 | 两条路径统一，防重复推送；缺店铺与站点会导致同款货在不同站点串单 |
| 作业形态 | 面单来源（平台面单 / 货主自带承运商 / 自提无面单）、时效等级（普通 / 当日 / 即时）、贴标与换标与塑封、是否允许拆包与一单多包裹 | 决定仓内如何作业；缺失则即使有订单也无法执行 |
| 随单文件 | 面单 PDF / ZPL、箱唛、装箱单由调用方随单推送；WMS 只负责打印与校验 | 守住「不直连平台」前提，避免被面单逼成平台对接 |

### 4.3 模块边界

- 平台枚举（15 平台 × 94 模式 × 114 条目）只允许出现在 `wms-integration` 的适配层与字典表。
- `wms-outbound`、`wms-task` 不认识平台名，只认 `source_type` 与作业形态字段。
- 将来启用直连平台，只是新增适配器向同一契约灌单，出库域无需改动。
- 平台仓库存（FBA 类）不进入可用库存，最多作为在途或参考数据。

## 5. 与现有 spec 的关系

现有 OpenSpec 规格覆盖仓库网络、平台管理（系统管理）、商品中心、客户管理，**没有销售订单与平台履约域**。本文是该域的前置材料，尚未绑定 change。进入实现时须在 `proposal.md` 中引用本文，并补齐第 7 节列出的缺口。
