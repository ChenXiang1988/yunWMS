# yunWMS 权限模型调研：RBAC 与三维数据权限

- 调研时间：2026-10-22
- 时效：本文为 2026-10-22 的快照，记录当时状态；后续变化以仓库现状为准，本文不回改。
- 数据来源：RuoYi-Vue 与 RuoYi-Vue-Plus 仓库源码与官方文档、Sa-Token 官方文档、Spring Security 官方文档、PostgreSQL 官方文档
- 结论状态：已采纳，对应 `design.md` D10 与 D18

## 1. 需求要点

| 维度 | 要求 |
| --- | --- |
| 主体 | 内部员工、货主账号两类，货主账号强制绑定 `owner_id` |
| 功能权限 | 菜单可见性、按钮可操作性、接口可调用性 |
| 数据权限 | 仓库、货主、库区三个维度取交集 |
| 特殊规则 | 未配置即无权；超级管理员自动拥有全部 |
| 许可 | 零商业授权，GPL/AGPL/SSPL 一律排除 |

## 2. 候选方案

| 方案 | 许可 | 权限点建模 | 数据权限 | 结论 |
| --- | --- | --- | --- | --- |
| RuoYi-Vue-Plus | MIT | 菜单表即权限点，`menu_type` 分目录/菜单/按钮 | 基于部门树，五种范围枚举 | 借建模与注解风格 |
| JeecgBoot | Apache-2.0 | 菜单与按钮分离两类表 | 基于部门 | 功能过重，低代码平台耦合深 |
| Pig4Cloud | Apache-2.0 | 同 RuoYi 系 | 基于部门 | 微服务形态，首期不用 |
| Spring Security | Apache-2.0 | 无内置模型 | 无 | 只做认证，权限模型自建 |
| Sa-Token | Apache-2.0 | 无内置模型 | 无 | 认证与会话选它 |
| PostgreSQL RLS | PostgreSQL License | 无 | 数据库层行级策略 | 作为加固选项，不作主路径 |

## 3. 权限点建模的两种形态

### A. 菜单表即权限点

RuoYi 用一张 `sys_menu` 承载目录、菜单、按钮三类记录，靠 `menu_type` 区分：

| 类型 | 含义 | 是否出现在侧栏 |
| --- | --- | --- |
| `M` | 目录 | 是，仅作为分组 |
| `C` | 菜单 | 是，对应一个路由与组件 |
| `F` | 按钮 | 否，只用于控制操作入口 |

每条记录带 `perms` 字段，格式为 `模块:实体:动作`，例如 `system:user:add`。角色通过 `sys_role_menu` 关联，用户的菜单树由后端拼装后返回前端动态注册路由。

**优点**：加一个页面等于加一条菜单记录加一个组件文件，不需要在代码里维护第二份权限清单；按钮权限天然挂在菜单下面，层级关系清楚。

**缺点**：`component` 字段存前端组件路径字符串，菜单数据与前端文件结构强耦合，改目录要同步改数据。

### B. 权限清单独立成表

权限点单独存一张表，菜单树另一张表，两者通过 `permission_id` 关联。

**优点**：权限点与界面解耦，同一权限可被多个菜单引用。

**缺点**：多一层关联，配置界面要维护两份数据，实际项目里很少用到「一权限多菜单」的能力。

### 结论

选 A。我们的权限点与菜单是一对一关系，独立成表只增加维护成本。同时把 `component` 的耦合风险控制在「改名时同步一条数据」，可接受。

## 4. 数据权限的三种实现

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A. 拦截器拼 SQL** | 在 MyBatis 拦截器里按注解追加 `where` 条件 | 实现直接、可控、能按接口定制维度 | 每个查询多一个条件，索引要覆盖 |
| B. 数据库行级安全 | PostgreSQL RLS，按 `current_setting` 过滤 | 无法绕过，安全性最高 | 调试困难，连接池要正确清理会话变量 |
| C. 应用层手工过滤 | 各 Service 自己写条件 | 无框架成本 | 漏一处就是数据泄露 |

RuoYi 用的是 A，注解形如：

```java
@DataScope(deptAlias = "d", userAlias = "u")
```

AOP 解析注解里的别名，拼接 `and (d.dept_id in (...) or ...)`。别名机制的好处是同一段切面能适配不同表的字段名。

**我们的选择**：A 作为主路径，注解改为三维：

```java
@DataScope(warehouseAlias = "w", ownerAlias = "o", zoneAlias = "z")
```

B 保留为将来的加固手段。一旦某类数据（如库存、账单）需要更强的隔离，可以对那几张表单独启用 RLS，与 A 并存不冲突。

## 5. RuoYi 的数据权限为什么不适用

| 项 | RuoYi | yunWMS |
| --- | --- | --- |
| 组织基础 | `sys_dept` 部门树 | 无部门树，组织仅用于归属 |
| 范围枚举 | 全部 / 自定义 / 本部门 / 本部门及以下 / 仅本人 | 仓库 / 货主 / 库区三选交集 |
| 配置位置 | 角色上 | 用户上 |
| 多角色叠加 | 取并集或最大范围，规则复杂 | 不做叠加，一用户一范围 |

根本差异在于**数据归属不是部门**：库位归仓库与库区，商品归货主，与公司组织架构没有对应关系。硬套部门树的结果是要为每个仓库建一个部门，最后部门树变成仓库树的影子，两套结构还要同步。

另外，RuoYi 把范围配在角色上。我们的仓库分工变动频繁，绑在角色上会导致「为一个人新建一个角色」的尴尬，所以配在用户上。

## 6. 认证部分

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 框架 | Sa-Token | 多端登录、踢人下线、账号封禁开箱即用，中文文档完整 |
| 注解 | `@SaCheckPermission("system:user:add")` | 与 RuoYi 的 `@PreAuthorize("@ss.hasPermi(...)")` 等价，少一层 SpEL |
| 第二因子 | TOTP（`dev.samstevens.totp`） | 不依赖短信通道，海外仓可用 |

## 7. 被否方案

| 方案 | 否决原因 |
| --- | --- |
| Spring Security + 自建 RBAC | 能力更强但配置重，首期只有两个端、几十个接口，用不上 |
| Keycloak / Casdoor | 独立部署身份服务，运维成本超过收益；将来要多系统 SSO 时再引入 |
| JeecgBoot 低代码 | 生成代码与平台强耦合，后期定制成本高 |
| PostgreSQL RLS 作为主路径 | 调试与运维成本高，且需要连接池严格清理会话变量，首期不划算 |
