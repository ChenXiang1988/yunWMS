单据引擎：四种行业解法
与本工作区的对照

“单据引擎”不是行业标准术语。它指四类能力的不同组合：单据建模、类型与编号、流转、转换与校验。本页拆开四种主流做法，给出机制、代价和适用条件，再对照本工作区已有的单据模型。

00

先分清三种所指

同一个词，在三个语境里指三套不同的东西。取用前先确认语境，否则会把财务单据的校验规则，误当成仓内作业的流程引擎。

订单中心 / 单据中心 交易与履约

配置对象是统一单据模型、扩展字段与接口收口。

目标是让多条业务线共用一套模型，新业务接入不改代码。

代表：京东物流订单中心、阿里交易域

单据类型 / 流程类型 ERP 与 WMS

配置对象是单据类型、仓库流程类型、任务与下推规则。

目标是让单据语义、现场动作与执行单元分开配置。

代表：SAP EWM、金蝶 BOTP

单据引擎 / 表单引擎 财务与费控

配置对象是单据模板、字段、校验规则与计算规则。

目标是让业务人员在提交前完成机器校验。

代表：中兴新云 FOL

本页的用法。本工作区的“单据引擎”接近第二类。它已有类型、流程、状态机、策略四件，没有单据转换规则与执行包层。第四节的对照按这个判断给出。
01

设计思路：四件事，不是一件

行业里能称为“引擎”的部分，通常由四件事组成。四件事可以分开做，也可以合成一个产品。差别不在技术栈，而在配置边界停在哪一层。

A

单据建模

单头、明细行、扩展字段。决定一张单能装什么。

B

类型与编号

类型决定语义、可用流程与编号段。决定一张单是什么。

C

流转

状态机与流程模板。决定一张单走到哪一步。

D

转换与校验

字段映射、分组、容差、校验规则。决定一张单如何变成下一张单。

一句话结论。行业做法的分歧集中在 D。只做 A 到 C 的系统，单据之间靠代码连接；把 D 也配置化的系统，才称得上“单据引擎”。
02

四种模式

每种模式给出机制、可落地的做法、代价与来源。模式名称取行业里的通用叫法，代表系统取公开可查的一手资料。

01

统一单据中心

最佳实践

互联网交易与履约语境。代表：京东物流订单中心、阿里交易域。

  • 一套模型收口所有业务线。单头、明细、扩展字段共用。不同业务只加类型与字段，不另建一套单据表。
  • 字段按域分组。京东把订单字段划成九类：主档、货品、物流服务、营销、财务、客户渠道、收发货、操作、扩展。标识类字段不逐项建列，走 KV 存储。
  • 个性化字段用三元组定位。按「业务身份 + 业务类型 + 业务字段」找到具体表与字段。每张表预留扩展属性，同一属性在不同业务类型下含义不同。
  • 两层收口。接口层做单据流量的唯一入口；数据层把持久化、搜索、中继、对账拆开。交易与履约解耦。
  • 聚合与事件。阿里以交易订单为聚合根，订单商品、发货单在聚合内创建；状态变化发领域事件。

可落地的做法

  • 先建字段字典，再谈扩展字段。
  • 扩展字段用 KV，不逐项加列。
  • 单据链只存上游单号与行号，不复制上游内容。
  • 状态变化单独留流水。
来源：S1S2
接入多条业务线
→
统一单据模型头 / 行 / 扩展字段
→
履约与执行按场景分发
收口做两层：接口层收单据流量，数据层收存储与查询。
02

单据类型 × 流程类型 × 任务 / 执行包

竞品案例

WMS 语境，与本工作区最接近。代表：SAP EWM。

  • 三层结构。仓库请求表达要做什么；仓库任务表达怎么搬、从哪到哪；仓库订单把任务组装成工作包，交给具体作业人员。
  • 流程类型挂在单据行上。仓库流程类型（WPT）分配给每个仓库请求行，控制该行的活动与任务创建方式。WPT 不同，是否自动建任务、建几个、进哪个队列都会不同。
  • 任务由单据派生。任务带源单号与行号。任务之上再按队列、活动区域、资源分组，形成执行包。
  • 单据链单独查。Document Flow 显示与一笔业务直接相连的前序、后续单据及其状态，形成单据链。
  • 类型与号段绑定。单据类型指定号码段，单号从号段中取。

可落地的做法

  • 单据行上挂流程类型，流程不画在单据上。
  • 任务带源单号与行号，作为幂等键。
  • 执行包按资源与队列聚合，不按单据聚合。
  • 提供上查、下查与全流程跟踪。
来源：S3S4S5S12
仓库请求要做什么。业务单据层，可回写上游。单据类型
仓库任务怎么搬。物理动作层，带源位与目标位。流程类型 WPT
仓库订单由谁、按什么顺序做。执行包层。队列 / 资源
这三层是本页最值得对照的结构。单据与执行单据分开，执行包可以跨单据合并。
03

单据转换 / 下推

竞品案例

国产 ERP 与财务语境。代表：金蝶 BOTP、中兴新云 FOL。

  • 转换规则定义字段映射。源单与目标单逐字段对应，携带数量、金额、批次等业务字段。
  • 分组策略决定基数。一对一生成、多对一生成、按规则分组合并生成。多对一时，单据头取第一张源单的值。
  • 尾差单独处理。金额或数量换算产生小数差时，按尾差策略调差，避免下游合计对不上。
  • 运行时五个动作。下推、选单、上查、下查、全流程跟踪。前两个生成下游单，后三个查单据链。
  • 校验前移。中兴新云把校验放在提交、业务审批、财务初审三个时点，形成“配置—提单—机审—人审”的闭环。

可落地的做法

  • 转换规则单独建表，不与页面逻辑混写。
  • 分组策略按单据类型固定，不逐单判断。
  • 数量与金额都要有容差口径。
  • 转换后保留源单行号，供追溯。
来源：S6S7
上游单源单与分录
→
转换规则字段映射 / 分组 / 尾差
→
下游单目标单与分录
单据类型关系支持 1 比 1、多比 1；1 比多时由系统自动选一个目标类型。
04

标准流程 / 决策引擎与元数据建模

行业标准

通用技术派。用标准建模语言或元数据平台承载流程与规则。

  • BPMN 2.0。OMG 的流程建模标准。流程图可以被流程引擎直接执行，适合跨系统的长流程。
  • DMN。OMG 的决策建模标准。用决策表或决策树表达“命中哪条规则”，适合策略判定。
  • External Task。Camunda 把系统动作发布成待办，由外部 worker 拉取执行。适合把 PDA、AGV、打印等设备动作挂到流程上。
  • 元数据建模。金蝶苍穹 KDDM 用元数据描述业务对象、布局、规则与流程，运行期动态加载。

可落地的做法

  • 流程与执行解耦，执行侧只认任务。
  • 策略用决策表，不用 if-else 堆叠。
  • 元数据要配版本与灰度。
  • 高频短流程不套通用引擎。
来源：S8S9S10S11
BPMN 2.0流程可执行标准。适合跨系统、带人工审批的长流程。
DMN决策表与表达式。适合上架、波次、路由等策略命中。
Camunda External Task外部 worker 拉取任务。适合设备与终端的异步动作。
金蝶 KDDM元数据描述对象、布局、规则、流程，运行期加载。
03

权衡取舍

四种模式都能解决“配置化”的问题，代价落在不同位置。失败条件比收益更值得先看。

模式收益代价失败条件
统一单据中心 新业务接入快，模型不膨胀，数据可跨业务分析。 扩展字段治理难，跨域查询与对账复杂。 没有字段字典与责任人，KV 变成垃圾场。
类型 × 流程类型 × 任务 / 执行包 单据语义与现场动作分离，任务可按资源聚合。 配置项多，流程类型与存储策略互相耦合。 流程类型粒度过细，配置数量爆炸。
单据转换 / 下推 单据链自动生成，减少重复录入，上下游可追溯。 字段映射与分组规则维护成本高，尾差与容差易错。 上下游类型一对多，追溯链出现断点。
BPMN / DMN 通用引擎 标准、可视、可审计，跨系统流程统一。 引擎与领域模型两张皮，简单单据被过度建模。 用 BPMN 画仓内高频短流程，开销大于收益。
元数据低代码 业务人员可自配，变更快。 运行期解释，性能与可测性下降。 缺少版本与灰度，配置错误直接影响生产。
04

适用场景

按约束选模式，不按技术偏好选。先回答单据种类、现场动作、转换频率三个问题。

条件选择理由
单据种类多、扩展字段多、多业务线共用 统一单据模型，再谈引擎 模型不统一时，配置化只会放大差异。
现场动作复杂，任务要按人、设备或队列聚合 单据 → 任务 → 执行包三层 执行包按资源聚合，不按单据聚合。
上下游转换频繁，如入库、收货、上架，或补货、拣货、移库 单独做转换规则表 字段映射、分组与容差需要独立维护与试算。
规则要由业务人员改，且要审计 DMN 决策表或规则表 决策表可版本化，命中结果可解释。
流程跨多个系统，含长事务与人工审批 BPMN 引擎加 External Task 通用引擎擅长长流程，不擅长秒级仓内任务。
05

与本工作区的对照

本节依据工作区内文件，不引用外部资料。判断口径：已有、缺口、风险三列。

已有W1

  • 类型注册表。wset-workflow.json 有 2 个单据、4 个类型。
  • 流程与工序。8 条仓库流程、4 个模板、16 个工序节点、9 类动作。
  • 状态机。2 套，分别有 7 条与 5 条迁移。节点只引用迁移，不新增状态。
  • 策略表。wset-strategy.json 有 7 条规则，按单据级与工序级分层。
  • 单据链。model.json 有 7 条关系，写明来源与派生。

缺口W1

  • 转换规则。全库检索不到下推、转换规则、上查、下查、全流程跟踪。
  • 执行包层。结构是主单据到作业任务，任务之上没有按资源或队列聚合的容器。
  • 编号规则。单号只是数据字段，没有号段与类型绑定的配置。

风险W1

  • 入口分散。流程、状态机、策略分三页配置。新增一个单据类型要改多处。
  • 页签由构建注入。类型页签在构建期写入，补货单还显式关闭了页签。
  • 监控页已撤。流程监控改由单据详情承载，没有独立的跨单据视图。

SAP EWM 三层

仓库请求 · 要做什么
仓库任务 · 怎么搬
仓库订单 · 由谁做

执行包可以跨单据合并，目标是资源效率。

本工作区两层
