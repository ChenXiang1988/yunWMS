# PRD 目录

## 定位

本目录下的 PRD 是 `openspec/` 中 spec 的**派生物**，不是独立事实来源。

- 事实只有一份，在 spec 里。
- 冲突时一律以 spec 为准，PRD 无条件让位。
- 不得在 PRD 中引入 spec 未定义的行为；发现需要补充时，回 spec 补，再重新生成 PRD。

## 一份 PRD 的边界

| 维度 | 边界 |
| --- | --- |
| 范围 | 一个 capability，与 `openspec/specs/<capability>` 一一对应 |
| 篇幅 | 15 页以内，一次阅读 30 分钟内读完 |
| 内容 | 见下方「必需的七节」 |

**必需的七节**：解决什么问题、角色与场景、功能范围（含明确不做）、主流程、界面、规则与异常、验收清单。

**不进 PRD 的**：表结构与索引、接口路径与参数、技术选型、排期与人力。这些属于 `design.md` 或项目计划。

字段表在 PRD 中只写「字段、用途、是否必填」，长度、格式、正则等约束指回 spec —— 约束会频繁微调，写进 PRD 会让文档天天变。

## 何时生成

判定标准一句话：**这个变更是否让用户看到不同的东西、做不同的事，或按不同规则操作。**

### 需要生成或更新

| 情况 | 说明 |
| --- | --- |
| 新增或删除功能、页面 | 用户能看到的东西变了 |
| 业务流程或步骤顺序变化 | 用户的操作路径变了 |
| 界面结构调整 | 页面布局、页签、入口变了 |
| 权限规则变化 | 谁能做什么变了 |
| 用户可感知的校验规则变化 | 以前能存现在不能存，或反过来 |
| 能力下线 | 需要标记为撤销 |

### 不需要生成

| 情况 | 说明 |
| --- | --- |
| 纯重构、性能优化 | 用户无感 |
| 内部接口调整、模块拆分 | 用户无感 |
| 依赖升级、框架版本变更 | 用户无感 |
| 修 bug 但行为与文档一致 | 文档本来就没写错 |
| 字段长度、正则、默认值微调 | 这类约束只在 spec 中维护 |
| 索引、分区、查询优化 | 属实现层 |

不确定时按「用户可感知」判：**让一个真实用户来操作，他会不会发现不一样。** 会，就更新；不会，就不更新。

### 谁来决定

在 `proposal.md` 里声明：

```markdown
## PRD 影响

- 受影响文档：`docs/prd/customer-profile.md`
- 变更性质：迭代
- 摘要：新增信用额度与账期管理
```

或明确写「无影响（纯内部重构，用户不可感知）」。

写在 proposal 里的好处是：作者在动工前就必须想清楚这件事，而不是事后补。

## 生成流程

```text
1. 判定：按「用户可感知」判断是否影响 PRD
2. 改 spec：所有需求变更先改 spec，走 OpenSpec change 流程
3. 归档 change：delta 合并进 openspec/specs/，形成稳定状态
4. 生成 PRD：读 openspec/specs/ 下对应 capability，按模板重排
5. 人工补充：只补线框图和名词解释，正文不改
6. 记录版本：changelog 追加一行，写明版本、对应变更、性质、摘要
```

change 尚未归档时，从 `openspec/changes/<change>/specs/` 读取，并在 PRD 头部标注「基于未归档变更」。

## 三种生成模式

| 模式 | 何时用 | 做法 |
| --- | --- | --- |
| **全量生成** | 初版，或章节结构发生调整 | 整篇重写 |
| **增量更新** | 单点变化，章节结构不变 | 只重新生成受影响的章节，其余保持原样，changelog 追加一行 |
| **不生成** | 用户不可感知 | 不动 PRD |

增量更新也算生成，不算手改 —— 改的是被重新生成的章节，不是文字润色。

## 生成前的就绪度检查

写 PRD 之前，逐项确认 spec 是否已具备以下五项。**任一项不满足，先补 spec。**

| # | 检查项 | 判定标准 |
| --- | --- | --- |
| 1 | 角色与权限 | spec 中有角色清单，且有「某角色可以 / 不可以做某事」的可测断言 |
| 2 | 完整生命周期 | 覆盖创建、编辑、状态流转、终止与异常分支，不只覆盖创建 |
| 3 | 界面承载 | spec 中列出每个界面的信息区块与操作入口（不要求视觉布局） |
| 4 | 字段约束 | 必填、长度、格式、唯一性、提示规则齐全，且可逐条枚举 |
| 5 | 验收场景 | 每个功能至少一条正向场景与一条异常场景，可直接转成测试用例 |

判定结果记录在 PRD 开头的「就绪度」小节，写明评估日期与评估人。

## 版本与变更记录

每个 PRD 顶部维护一张版本表，最后一行是当前版本。

```markdown
| 版本 | 日期 | 对应变更 | 性质 | 摘要 |
| --- | --- | --- | --- | --- |
| v1.0 | 2026-10-22 | init-wms-foundation | 初版 | 货主档案、联系人、税号、合作仓、合同、账号 |
| v1.1 | 2026-12-05 | add-owner-credit-limit | 迭代 | 新增信用额度与账期管理 |
```

「性质」列必须填，它决定了读者如何理解这次改动：

| 性质 | 含义 |
| --- | --- |
| 初版 | 第一次成文 |
| 迭代 | 需求往前走，行为跟着变，不是之前写错 |
| 纠错 | 之前确实写漏或写错 |
| 撤销 | 某个能力下线，不是出错 |

旧版本文件不必保留，git 有完整历史；但 changelog 必须完整，因为它是给人读的。

## 与 spec 的分工

| 内容 | 归属 |
| --- | --- |
| 行为断言（SHALL / MUST、场景） | spec |
| 字段约束（长度、格式、唯一性） | spec |
| 界面信息区块与操作入口 | spec |
| 背景、目标、用户画像 | PRD |
| 功能清单与优先级 | PRD |
| 权限矩阵表格 | PRD（由 spec 断言汇总） |
| 流程图与线框图 | PRD |
| 验收清单 | PRD（由 spec 场景汇总） |

PRD 里凡是能指回 spec 的，都指回去，不抄细节。

## 禁止事项

1. **禁止手改正文**。发现需要改，回 spec 改，再重新生成。
2. **禁止在文档里写「此节已废弃」**。废弃内容应在 spec 中删除，PRD 重新生成后自然消失。
3. **禁止静默发布新版本**。每次变更都要在 changelog 留痕。
