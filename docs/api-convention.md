# 接口契约规范

适用于全部 HTTP 接口。前后端都以此为准，前端 **MUST NOT** 依赖契约之外的字段。

## 一、路径

```text
/api/{资源复数}              列表、新建
/api/{资源复数}/{id}         详情、更新
/api/{资源复数}/{id}/{动作}  状态流转等非 CRUD 操作
```

- 路径 **MUST** 用资源名词复数，**MUST NOT** 出现动词，状态流转除外（如 `/disable`、`/submit`）。
- 前端两端的接口前缀分别是 `/api/console`（仓网端）与 `/api/portal`（货主端），用于区分鉴权主体。
- 复杂筛选（条件超过 5 个或含数组）**MAY** 走 `POST /api/{资源}/search`，其余查询 **MUST** 用 GET + query。

## 二、响应结构

**所有接口统一返回 `ApiResult`，HTTP 状态码固定 200。**

```json
{ "code": 0, "message": "成功", "data": {} }
```

**唯一例外**：未认证返回 401，无权限返回 403。这两个 **MUST** 用 HTTP 状态码，因为前端要靠它决定「跳登录页」还是「提示无权」，混用会把用户卡在原地。这两个响应体同样是 `ApiResult`。

## 三、错误码

五位整数，前三位对齐 HTTP 语义，后两位是同段内的序号。

| 段位 | 用途 |
| --- | --- |
| `0` | 成功 |
| `400xx` | 请求参数问题 |
| `401xx` | 未认证 |
| `403xx` | 无权限 |
| `404xx` | 资源不存在 |
| `409xx` | 数据冲突（唯一约束、状态不允许） |
| `500xx` | 服务内部错误 |

新增错误码 **MUST** 加在对应段位内，**MUST NOT** 跨段复用。

## 四、分页

请求：

```json
{ "pageNo": 1, "pageSize": 20 }
```

响应 `data`：

```json
{ "pageNo": 1, "pageSize": 20, "total": 137, "records": [] }
```

- `pageNo` **MUST** 从 1 开始。
- `pageSize` **MUST** 受上限约束（200），超出 **MUST** 拒绝而不是静默截断。
- `total` 是总数，不是本页条数。

## 五、字段类型

- **ID 在 JSON 中以字符串传输。** Java `Long` 超过 2^53 会使 JS 丢精度，等到出问题再改要动全部前端。
- **时间用 ISO 8601 带时区**，如 `2026-10-24T08:30:00Z`。库内统一 UTC，展示层转换。
- **枚举用字符串编码**，值取自后端定义的枚举名，**MUST NOT** 用序号。
- **布尔**用 `true` / `false`，**MUST NOT** 用 `1` / `0`。
- **空集合**返回 `[]`，**MUST NOT** 返回 `null`。

## 六、请求体

- 字段 **MUST** 与后端 `Request` 类一一对应，多余字段后端 **MUST** 拒绝（`FAIL_ON_UNKNOWN_PROPERTIES`），**MUST NOT** 静默忽略——忽略会让前端以为改生效了。
- 更新接口 **MUST** 明确是全量替换还是部分更新，同一接口 **MUST NOT** 混合两种语义。
- 业务标识（如货主编码）**MUST** 放在请求体或路径中，**MUST NOT** 放在自定义 header。

## 七、幂等

以下入口 **MUST** 有幂等策略，并 **MUST** 在契约中写明：

| 入口 | 策略 |
| --- | --- |
| 批量导入 | 同货主同时只允许一个进行中任务 |
| 状态流转（审核、终止） | 目标状态与当前状态相同时返回成功，不报错 |
| 定时任务触发的提醒 | 按「业务对象 + 提醒类型 + 时间窗」去重 |

**MUST NOT** 用「查一下再插入」实现幂等，并发下无效。**MUST** 用数据库唯一约束或分布式锁。

## 八、OpenAPI

- 接口 **MUST** 有中文 `summary` 与 `description`，说明业务语义而非复述路径。
- **MUST NOT** 在每个接口重复声明 401/403/500 的响应，这些由全局配置统一描述。
- 请求与响应模型的字段 **MUST** 带 `description`。
- 契约变更 **MUST** 与实现同一次提交，**MUST NOT** 先上代码后补文档。

## 九、契约先行（跨端接口）

### 适用范围

本节只适用于**跨端接口**：同一个接口既要后端实现、又要前端页面消费。

单侧接口（只有后端消费，例如内部任务、数据回填）**不适用**，仍按第八节与实现同一次提交，不为它多走一轮。

### 为什么

人类团队里，前端发现字段不对会去问后端，中途就能纠正。AI 实现里两侧不通信：子 Agent 各有独立上下文、互相看不见，只能回主 Agent，而主 Agent 在同步派发期间被挂起。两边对不上时只剩两条路——编造，或停下；后者意味着一次任务白跑。

把契约从「文档」升级为「已提交的代码」，分歧才会变成可见的冲突，而不是两份文档的静默不一致。

### 要求

1. **MUST** 先提交只含签名、不含实现的契约：Controller 接口 + 请求/响应 DTO + 枚举。不含 Service 实现、不含 SQL、不含仓储层。
2. 该提交 **MUST** 单独一次，不夹带实现，以便两侧在它上面分叉。
3. 实现阶段 **MUST NOT** 修改已提交的契约签名。需要变更时停下回主 Agent，由主 Agent 决定改契约还是改需求。
4. 前端实现的取数边界是 `docs/api/`，**MUST NOT** 阅读 `code/backend/**`。读了会耦合到 DTO 内部字段与 Service 方法，前后端分离只剩目录形态。
5. 契约提交后 **MUST** 重跑台账生成，否则前端拿到的是旧字段。生成方式见 `docs/api/README.md`。

### 与第八节的边界

第八节「契约变更 MUST 与实现同一次提交」针对**尚无第二方消费**的接口；本节针对**已有一侧按其编码**的接口。

判据只有一条：**是否已有另一侧按该契约在写代码**。已有时，任何契约修改都必须单独提交，即使只是一次实现中的「顺手优化」。
